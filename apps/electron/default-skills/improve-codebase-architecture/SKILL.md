# Improve Codebase Architecture(寻找深化机会)

> 基于 [mattpocock/skills](https://github.com/mattpocock/skills)(MIT License, Copyright 2026 Matt Pocock)改造。

暴露架构摩擦,提出**深化机会**——把浅模块变成深模块的重构。目标是可测试性与 AI 可导航性。本技能以项目的领域模型为输入:领域语言给出好 seam 的命名,ADR 记录不该被重议的决策。

## 词汇表

提出建议时**精确使用这些词**,不要漂移到"组件""服务""API""边界":

- **模块(Module)** — 任何有接口与实现的东西(函数、类、包、切片)。
- **接口(Interface)** — 调用者必须知道的一切:类型、不变量、错误模式、顺序、配置。不只是类型签名。
- **实现(Implementation)** — 接口背后的代码。
- **深度(Depth)** — 接口处的杠杆:小接口背后藏着大量行为。**深** = 高杠杆;**浅** = 接口几乎和实现一样复杂。
- **Seam** — 接口所在之处;不改原地就能改变行为的位置。(用 seam,不用"边界"。)
- **适配器(Adapter)** — 在 seam 处满足接口的具体实现。
- **杠杆(Leverage)** — 调用者从深度中得到的好处。
- **局部性(Locality)** — 维护者从深度中得到的好处:变更、bug、知识集中在一处。

关键原则:

- **删除测试**:想象删除这个模块。如果复杂度随之消失,它就是过路层;如果复杂度在 N 个调用者处重新冒出来,它就在挣它的位置。
- **接口就是测试面。**
- **一个适配器 = 假设的 seam;两个适配器 = 真实的 seam。**

## 流程

### 1. 勘察

先读项目的领域词汇(CONTEXT.md 或等价文档)与相关区域的 ADR。

然后实地走一遍代码库(Read/Grep/Glob),**不要套僵化清单**,有机地探索,记下你体验到摩擦的地方:

- 理解一个概念要在很多小模块之间跳来跳去的地方;
- 模块**浅**的地方——接口几乎和实现一样复杂;
- 纯粹为了可测试性抽取的纯函数,但真正的 bug 藏在调用方式里(没有**局部性**);
- 紧密耦合的模块在 seam 处互相泄漏;
- 哪些部分没测试,或很难通过当前接口测试。

对任何疑似"浅"的东西应用**删除测试**:删掉它会集中复杂度,还是只是挪动复杂度?"集中了"才是你要的信号。

### 2. 呈献候选

给出编号的深化机会清单。每个候选包含:

- **Files** — 涉及哪些文件/模块;
- **Problem** — 当前架构为什么造成摩擦;
- **Solution** — 用平实的语言描述会怎么变;
- **Benefits** — 用局部性与杠杆解释,同时说明测试会怎么变好。

**领域词汇用 CONTEXT.md 的,架构词汇用本技能词汇表的。** 如果 CONTEXT.md 把某概念定义为"Order",就说"Order intake 模块",而不是"FooBarHandler",也不是"Order 服务"。

**ADR 冲突**:候选与现有 ADR 冲突时,只有摩擦真实到值得重开决策才提出,并明确标注(如"与 ADR-0007 冲突——但值得重开,因为……")。不要列一堆 ADR 禁止的理论重构。

**此阶段不要提具体接口方案。** 呈献完问用户:"想深入哪个?"

### 3. 质询循环

用户选定候选后,进入质询式对话:约束、依赖、深化后模块的形状、seam 背后放什么、哪些测试能存活,一步步把设计树走完。决策在对话中即时沉淀:

- **用了一个 CONTEXT.md 之外的概念命名深化后的模块?** 把术语补进 CONTEXT.md(文件不存在就懒创建)。
- **对话中磨尖了某个模糊术语?** 就地更新 CONTEXT.md。
- **用户用承重理由否掉了候选?** 提议记一条 ADR:"要不要我记成 ADR,免得以后的架构审查重新提这个?"只有未来探索者确实需要它来避免重复建议时才提议——跳过临时性理由("眼下不值得")和自明理由。

## 何时不该用本技能

- 局部 bug 修复、命名清理、单文件小重构:直接做,不要展开候选清单和质询循环。
- 用户只想了解代码结构(说明性问答):直接解释,不要产出重构提案。
- 新项目/没有 CONTEXT.md 也没有 ADR 的仓库:先确认用户是否想建立领域词汇,再走本流程。
