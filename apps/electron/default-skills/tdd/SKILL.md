# Test-Driven Development(红绿重构)

> 基于 [mattpocock/skills](https://github.com/mattpocock/skills)(MIT License, Copyright 2026 Matt Pocock)改造。

## 核心原则

**测试通过公共接口验证行为,而不是实现细节。** 代码可以整个重写,测试不该变。

- **好测试**是集成式的:走真实代码路径,经由公共接口。它描述系统"做什么"而不是"怎么做"。好测试读起来像规格说明书——"用户可以用有效购物车结账"精确描述了系统具备的能力。这些测试能扛住重构,因为不关心内部结构。
- **坏测试**绑死在实现上:mock 内部协作者、测私有方法、绕过接口直接查内部状态。警告信号:重构后行为没变但测试挂了。如果你改个内部函数名就挂一批测试,那些测试测的是实现不是行为。

## 触发决策:按意图或风险选择,不按任务类型泛触发

Agent 自行判断是否需要本技能,不要仅为了决定“要不要 TDD”而询问用户。

满足任一条件时使用:

- 用户明确要求 TDD、红绿重构、先写测试、测试先行或 BDD。
- 变更触及安全、权限、计费、数据一致性、数据迁移、并发等高代价边界。
- 业务存在多状态转换或关键不变量,实现出错会造成难以发现的行为偏差。
- bug 可通过公共接口稳定复现、容易再次回归,先写失败测试能明确锁定修复契约。
- 实现存在多种合理方案,需要先用行为测试钉住公共接口与验收边界。

下列情况默认不使用完整 TDD 流程:

- 任务只是普通新功能或普通 bug 修复,没有上述风险证据。
- 小型 CRUD、字段透传、小交互、低风险 wiring、样式文案、配置项或明显的局部修复。
- 现有测试已经充分覆盖目标行为,只需实现后运行聚焦回归。
- 快速原型、一次性脚本,或用户明确要求先实现再补测试。

风险处于中间地带时,优先直接实现并补一条必要回归测试、运行聚焦验证;不要默认升级为完整红绿重构循环。

## 反模式:水平切片

**不要先写完所有测试,再写所有实现。** 这是"水平切片"——把 RED 当成"写全部测试",把 GREEN 当成"写全部代码"。它产出烂测试:

- 批量写出的测试测的是"想象的行为",不是"实际的行为";
- 你在测试数据结构的形状,而不是用户可见的行为;
- 测试对真实变化失去敏感性——行为坏了它可能还过,行为没坏它反而挂;
- 你在理解实现之前就锁死了测试结构,把车灯范围之外的路给铺了。

**正确做法:垂直切片(垂直追踪弹)。一次一个测试 → 一个实现 → 循环。** 每个测试都回应上一个循环里学到的东西。因为你刚写完实现,你精确知道什么行为重要、怎么验证。

```
错误(水平):
  RED:   test1, test2, test3, test4, test5
  GREEN: impl1, impl2, impl3, impl4, impl5

正确(垂直):
  RED→GREEN: test1→impl1
  RED→GREEN: test2→impl2
  RED→GREEN: test3→impl3
```

## 工作流

### 1. 规划

写任何代码之前:

- 先读项目的 CLAUDE.md、CONTEXT.md(领域语言)与相关 ADR——测试命名和接口词汇必须匹配项目的语言,不要重议已有决策。
- 从需求与现有公共接口确定需要哪些接口变化、优先测哪些行为;只有目标存在实质歧义且无法合理推断时才询问用户。
- 列出要测的**行为**(不是实现步骤)。
- 你不可能测所有东西。聚焦关键路径和复杂逻辑,跳过显然无风险的分支;Agent 应自行确定优先级,不要增加例行确认。

### 2. 红绿重构循环(每个垂直切片)

1. **RED**:写一个失败的行为测试。测试名字描述行为("可以结账""拒绝无效令牌"),不描述实现。跑一次,确认它因为正确的原因失败(断言失败,而不是语法错误/导入错误)。
2. **GREEN**:写最少实现让测试通过。禁止顺手加"以后可能用到"的代码。
3. **REFACTOR**:测试绿着的时候清理实现——消除重复、改善命名;只动实现,不动测试语义。
4. 循环下一个行为。

### 3. 收尾

- 每个切片完成后跑一次相关测试;全部完成后集中跑受影响包的相关测试 + 必要的 `bun run typecheck`。
- 测试命令以项目为准(如 `bun test <file>`,或 package.json 中定义的脚本);先读项目文档确认,不要默认一个命令。

## 与仓库惯例的配合

- 如果项目明确要求 BDD(行为驱动开发),测试框架选择、命名风格与目录位置以项目 CLAUDE.md/文档为准。
- 如果项目已有失败测试的验证约定(先红后绿),严格遵守;不要"顺手补绿"糊过红阶段。
- 本技能只约束测试纪律,不替项目决定测试框架、目录或 CI 配置。

## 何时不该用本技能

- 不得仅因任务属于新功能或 bug 修复而使用;先看风险、回归概率和测试先行的实际收益。
- 用户明确要"先出代码,测试后补",或任务是一次性脚本/临时探索代码。
- 普通 CRUD、小字段或小交互、低风险 wiring、明显局部修复、纯样式、文案、配置项调整:直接实现并运行必要的现有测试即可。
- 快速原型阶段:项目有 prototype 类流程时按项目约定走。
