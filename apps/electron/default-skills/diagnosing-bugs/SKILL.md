# Diagnosing Bugs(排查纪律)

> 基于 [mattpocock/skills](https://github.com/mattpocock/skills)(MIT License, Copyright 2026 Matt Pocock)改造。

排查难以定位的 bug 与性能回归时,遵循本纪律。只有在理由充分时才跳步。**本技能的核心是"先建立反馈回路",其余都是机械动作。**

## 第 1 步:建立反馈回路(最重要)

如果你能拿到一个**快速、确定、可由 Agent 自动运行**的"过/不过"信号,就一定能找到原因——二分、假设验证、埋点都只是在消费这个信号。没有信号,盯着代码看多久都没用。

在信号上投入不成比例的努力。**要激进、要有创造力、拒绝放弃。** 按以下顺序尝试:

1. **现有信号**:先运行最聚焦的现有测试、命令或固定输入，确认问题确实存在。
2. **脚本复现**:`bun test` 跑一个最小 fixture,对照已知正确的输出。
3. **CLI 调用**:用固定输入调用命令行,对比 stdout 快照。
4. **浏览器/接口脚本**:驱动真实 UI 或 HTTP 接口,断言 DOM/控制台/响应。
5. **回放捕获**:把真实的请求/事件/日志存成文件,在隔离环境里重放该代码路径。
6. **一次性 harness**:拉起系统最小子集(单个函数 + mock 依赖),直接触发 bug 路径。
7. **属性/模糊循环**:如果 bug 是"偶尔输出错",跑 1000 个随机输入找失败模式。
8. **二分 harness**:如果 bug 出现在两个已知状态之间(commit/数据集/版本),自动化"在状态 X 启动 → 检查 → 重复",支持 `git bisect run`。
9. **差分回路**:同一输入跑新旧两版,对比输出差异。
10. **失败测试**:当 bug 能经公共接口稳定复现、回归代价高或用户明确要求 TDD 时，写一个失败行为测试锁定契约。
11. **最后手段**:人工在环的脚本化流程,保持结构化,捕获的输出回流给你。

建立反馈回路不等于自动触发完整 TDD。普通局部 bug 可以先用现有命令/fixture 复现，修复后补必要回归；只有用户明确要求测试先行，或 seam 命中安全、权限、计费、数据一致性、迁移、并发、关键业务不变量等高风险门槛时，才按 `tdd` Skill 走完整 Red/Green。

### 信号定义

- 明确写出"通过"的标准:退出码、输出匹配、文件内容、DOM 状态。
- 信号必须在 30 秒内可跑完。慢信号要先缩小范围。
- 信号必须与 bug 同因:**信号失败 ⟺ bug 存在**。宁可重写信号,不要用不相关的检查糊弄过去。
- 拿到信号后,**跑一次**确认它在当前代码上确实失败。没有失败信号,继续回到本步骤。

## 第 2 步:最小化

把复现缩到最小:能删的都删掉(无关代码、依赖、数据、配置),每删一步都跑一次信号确认 bug 还在。最小化同时缩小"可能出错的代码"和"需要检查的假设"两个集合。

## 第 3 步:假设 → 验证

用证据驱动,不要靠直觉乱猜:

1. **只依据观察,不依据习惯**:在提出假设前,先收集具体事实(报错堆栈、日志、状态快照)。
2. **给每个假设打分**:按"能解释全部观察的概率"排序。
3. **并行验证可并行部分,串行验证依赖部分**:同一批互不依赖的读操作(Read/Grep/Glob)集中到同一工具批次。
4. **快速证伪优先于缓慢证明**:设计一个能一举排除某个假设的检查。
5. **记录每个被证伪的假设**:避免绕回已经排除的死路。

## 第 4 步:修复

- 只修 bug 的**根因**,不要给症状打补丁。
- 修改前检查周围代码是否有同类缺陷(复制粘贴的 bug)。
- 用最小 diff 表达修复;如果修复需要多个文件,一次只改一个假设点,改完立刻跑信号。

## 第 5 步:回归测试

修复后必须跑:

1. **信号转正**:原始失败信号现在必须通过。
2. **必要时转测试**:bug 能稳定复现、再次回归概率高或触及关键契约时，把复现固化为自动化测试；明显单行修复且已有覆盖时不为流程形式新增低价值测试。
3. **周边回归**:跑受影响模块的相关测试与 `bun run typecheck`(触及类型边界时);不要默认跑全仓。
4. **排查复盘**:如果排查走了弯路,把"为什么绕路"一句话记下来——值得沉淀的教训按 Domi 知识维护架构写入 Memory 或项目 CONTEXT.md。

## 何时不该用本技能

- 报错信息已指向明确的单行问题(拼写、类型、参数顺序),直接修复即可。
- 用户明确要求"按我说的改",不是要你定位问题。
- 性能问题在 30 秒内无法建立任何自动信号,且用户只想要一句话解释——先用 Read/Grep 做一次快速勘察,不要展开完整排查流程。
